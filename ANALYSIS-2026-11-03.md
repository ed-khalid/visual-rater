## 2. The playlist rater calculates scores incorrectly (Read)

Location: `frontend/src/components/raters/playlist/PlaylistRater.tsx`, `handleDragEnd`.

- **Neighbours are taken from the list before the move.** `itemBefore = items[newIndex-1]` and `itemAfter = items[newIndex]` are read before `arrayMove`.
  - Dragging a song down picks the wrong neighbours. Moving index 0 to index 1 makes `itemBefore` the dragged song itself.
  - The new score is therefore calculated from the wrong songs.
  - A discarded uncommitted change, now saved as a patch, fixed this by moving first and then reading the neighbours.
- **The state object is mutated directly.** The tie case runs `itemBefore.score = itemBefore.score! + 0.02`, which changes an object that came from the Apollo query result. Apollo freezes those objects in development, so this probably throws (not reproduced). Either way it changes data without going through React state.
- **Ties can break the order.** The +0.02 bump on `itemBefore` never checks the song above it, so it can move past that song.
- **Scores aren't clamped.**
  - Dropping a song at the top adds 0.01 and can go above 100.
  - Dropping a song at the bottom subtracts 0.01 and can go below 0. The backend treats any negative score as "clear the score" (`MusicCrudService.updateSong`), so a song scored 0 dragged to the bottom loses its rating.
- **Later pages use different filters.** The first page is queried with `{...songFilters, ...playlistFilters}`, but `fetchMore` sends only `playlistFilters`. Page 2 onwards can come from a different query, so later drags compare against the wrong songs.

## 3. Failed saves go unnoticed (Reproduced in part)

- `frontend/src/components/raters/RaterManager.tsx:17` sends `updateSong` and never checks the result, with no error handling and no optimistic response. The rater shows the new position whether or not the save worked.
- The backend has no range check on `score`.
- An unknown song ID calls `Optional.get()` and fails. Reproduced: `updateSong` with an all-zeros UUID returns `INTERNAL_ERROR`.

## 4. Backend filters are broken (Reproduced)

All in `backend/.../services/MusicCrudService.kt`.

- **Year filter crashes.** `songs(params:{year:1991})` returns `INTERNAL_ERROR`. `songFilterSpec` applies Postgres's `year()` function to `album.year`, which is already a plain integer.
- **Genre filter is ignored.**
  - The schema (`queries.graphqls`) names the argument `genre: [String!]`, but `QueryModels.kt` names the field `genres: List<Genre>`. Spring never binds it, so the filter is dropped without an error.
  - Even if it bound, the spec requires a match on the primary genre *and* a secondary genre (an inner join on the primary genre), where it should accept either.
- **Artist paging is fixed.** `readArtists` hardcodes `PageRequest.of(0, 50, …)` and ignores `pageNumber`.

## 5. Data integrity (Read, plus a DB check)

- **Re-importing an artist duplicates every album.**
  - `createArtist` returns an existing artist with the same *name*, but `createAlbum` never checks `vendorId`, so every album and song is inserted again.
  - Matching on name also merges two different Spotify artists who share a name.
  - `createAlbumsForExternalArtist` isn't a single transaction, so a Spotify or imageservice failure partway through leaves a half-imported artist.
  - No duplicates exist in the DB today.
- **Album totals go stale.** `trigger_album_total_recalc` (`db/04.song_score_update.sql`) fires `AFTER INSERT` on `album` only. Deleting an album never updates `artist_metadata.total_albums`. This is likely the cause of the todo item "DB: total album metadata is not updating".
- **Dead code in the migration.** `recalculate_tier()` in the same file creates a temp table and has no trigger attached.

## 6. Live updates are fragile (Read)

- `PublisherService.subscribe` adds the subscriber to a list but never calls `onSubscribe`, never honours `request(n)`, and never removes a subscriber.
  - This breaks the Reactive Streams protocol.
  - Subscribers from closed browser tabs pile up and keep getting `onNext` calls, which is a slow leak.
- `ArtistPublisherService` duplicates `ArtistPublisher` and is unused.

## 7. The docs give the wrong score range (Reproduced)

- `CLAUDE.md` and `frontend/README.md` describe scores as about 1–5 in 0.25 steps.
- Everything else uses 0–100:
  - Live DB: 1,243 rated songs out of 1,712, range 5–96.01, average 64.15.
  - The tier thresholds in the trigger (95/90/85/…).
  - `SCORE_END = 100` in `CoreModels.ts` and the thresholds in `ScoreModels.ts`.
  - The linear rater's scale range `[100, 0]`.
  - The grid's 100 blocks.
- Anyone, human or agent, who trusts the docs will get scoring logic wrong.

## Minor

- `show-sql: true` while root logging is `ERROR`: noisy and inconsistent.
- `spring.sql.init.mode: always` with no `schema.sql` or `data.sql`, so it does nothing.
- `logging.level.org.spingframework.web` is misspelled (`sping`), so the setting has no effect.
- `ddl-auto: update` re-runs `ALTER COLUMN … text[]` on `album` and `artist` at every startup.

## Suggested order

1. Repair the frontend test setup (`testhelpers.ts`, the stale reducer test) and add unit tests for the playlist score calculation, pulled out into a pure function.
2. Fix the playlist rater: pick neighbours after the move, stop mutating state, clamp to 0–100, handle ties properly, and use the same filters in `fetchMore`.
3. Validate scores and IDs in `updateSong` on the backend, and handle mutation errors on the frontend.
4. Fix the year and genre filters and artist paging.
5. Make artist import idempotent: dedupe albums by `vendorId`, match artists by Spotify ID, and use one transaction.
6. Add a delete trigger for `total_albums` as a new numbered migration.
7. Replace the hand-written publisher with a Reactor `Sinks.Many`.
8. Correct the score range in `CLAUDE.md` and `frontend/README.md`.
