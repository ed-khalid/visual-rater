# Visual Rater

A personal rating app whose point is the *rating interaction itself*: visual, drag-driven raters instead of star or number inputs. v1 (`frontend/`, `backend/`, `imageservice/`) rates music. v2 (`v2/`) is a from-scratch minimalist rebuild for ranking any type of item, with music first. On this branch (`v2-modern-magazine`) v2 is a 2D page styled like a news magazine; the 3D version is on `v2-scifi-3d`.

Project notes, status, and Progress History are kept outside this repo in `~/projects/04-todo/code-visual-rater/AGENTS.md`. If that folder has moved, look in the other status folders under `~/projects/`. Record design decisions and progress there, not here.

## Layout

This is a monorepo built from three formerly separate repos. Each history was rewritten into a subfolder (see `~/code/create-visual-rater-monorepo.sh`).

| Folder | Stack | Port |
|---|---|---|
| `frontend/` | React 19, TypeScript, Vite, Apollo Client, D3 7, dnd-kit, motion | 3000 |
| `backend/` | Kotlin, Spring Boot 3.4 (spring-graphql, JPA/Hibernate), Arrow, Postgres | 9000 |
| `imageservice/` | Python, FastAPI: dominant colors and image similarity for cover art | 7011 |
| `v2/` | React 19, TypeScript, Vite 8, motion (animations), zustand, cmdk, Newsreader and Inter fonts (@fontsource); small Hono API server in `v2/server/` | 3001 (app), 3002 (API) |

v1 request flow: frontend → GraphQL (HTTP for queries and mutations, WebSocket for subscriptions) at `localhost:9000/graphql` → backend → Postgres, Spotify Web API, imageservice.

v2 doesn't use any of that. Its own API server (`v2/server/`) holds the Spotify secret for lookups and saves everything to its own Postgres database, `visual_rater_v2`.

## Running locally

1. **Postgres:** database `visual_rater`, user `visual_rater_app`, on `localhost:5432`.
2. **imageservice:** `cd imageservice && .venv/bin/python main.py` (listens on 7011).
3. **backend:** `cd backend && ./gradlew bootRun`. Set `VISUAL_RATER_DATABASE_PW` and `VISUAL_RATER_SPOTIFY_CLIENT_SECRET` in the environment.
4. **frontend:** `cd frontend && npm install && npm start`. The backend URL is hardcoded in `src/setupApollo.ts`.

v2 runs on its own: `cd v2 && npm install && npm run dev` starts the app (3001) and the API server (3002) together. `npm run dev:web` and `npm run dev:api` start them separately. The API needs:
- **Postgres database `visual_rater_v2`**, owned by `visual_rater_app` (create it once: `sudo -u postgres createdb -O visual_rater_app visual_rater_v2`). The server connects with `VISUAL_RATER_DATABASE_PW`, the same variable v1 uses, or `V2_DATABASE_URL` to override. Without a database, the app shows "Can't reach the server."
- `VISUAL_RATER_SPOTIFY_CLIENT_SECRET` (shared with v1); without it, music suggestions are off.

## Frontend

- GraphQL documents live in `src/graphql/{queries,mutations,subscriptions,fragments}/*.graphql`.
- `src/generated/graphql.tsx` and `graphql.schema.json` are generated. Don't edit them by hand. Regenerate with `npm run graphql`, which needs the backend running because it introspects `localhost:9000/graphql`.
- State: reducer and providers in `src/music/` and `src/providers/`, data hooks in `src/hooks/`.
- Raters are in `src/components/raters/`:
  - `linear/`: D3 circles on a scale, with comparison songs
  - `grid/`: block/grid placement
  - `playlist/`: drag to reorder; the new score is interpolated from the neighbors' scores
- `deprecated/` holds old code kept for reference. Don't build on it.
- Checks: `npm run typecheck`, `npm test` (vitest).
- `todo.md` is the running backlog.

## Backend

- Package `com.hawazin.visualrater`: `controllers/` (GraphQL resolvers), `services/` (Spotify, imageservice, publishers for subscriptions), `configurations/`.
- Schema: `src/main/resources/graphql/*.graphqls`. After any schema change, regenerate the frontend types.
- Tests: kotest and mockk, run with `./gradlew test`. Coverage is thin.

## v2

- **Layout:** `src/scene/` is the board, a 2D page of DOM elements (`Board.tsx`: the rater's spine and scale, the marks on it, split view's row; `anchors.ts` publishes where things are on screen; `view.ts` the view state). `src/hud/` holds the DOM overlays around it: masthead and corner keys, catalog, type picker, ADD palette, album view, hover card. `src/state/` has the zustand store and pure layout logic (`place.ts` places marks on a rater). `src/shared/` has types shared with the server.
- **Look (this branch):** a magazine page: warm off-white paper, black ink for text, rules and borders, one red (`--accent`) for emphasis; tier and grade colours stay wherever they mean something (cover rings, chips, bars). Headlines and numbers in Newsreader, labels and controls in Inter (`src/index.css` has the variables). Cards are paper with an ink border and a hard offset shadow. Everything animates (motion for the board, CSS for the overlays): marks grow out of the spine on their leaders and draw back in, the spine and scale draw in, panels and rows rise in staggered. No 3D.
- **Data model:** no generic items or boards. Each type (MUSIC, MOVIES, BOOKS; constants in `src/shared/model.ts`) is one tree, built from that type's own collections: `artists`, `albums` and `tracks` for music, and `movies` and `books`. Anything rated directly (tracks, movies, books) carries its own `score` (0–100, undefined = unrated), its `branch` on the tree (`angle`, `length`, `ring`; from the 3D version, still stored and kept up by the store, but the 2D board ignores it), `since` and `hidden`. What each tree shows is worked out in `src/state/board.ts`, never stored: fruit = rateables with a branch that aren't hidden (on MUSIC, songs only come out in album view, split view, or while a typed entry is being rated: the default MUSIC view is the read-only rater, below); Misc's cover is drawn, never stored: black with SINGLES in white (`scene/cover.ts`, `albumCover`), also worn by its songs that have no picture of their own (`trackCover`: on any album, a song with no picture of its own shows its album's cover). Misc has no album score or grade (`rating` gives none), isn't on the Career chart, the Albums zoom or the FLOW chart, and sorts last among the artist's albums; its songs count for the artist as usual. Albums are made by hand there: ADD ALBUM in artist view's Albums section (desktop) opens a card (`hud/NewAlbum.tsx`) for title, year, cover (a link or an upload) and songs, one per line; the album goes on the tree at once, every song unrated (skits marked, live ones matched as usual; `store.createAlbum`), and album view opens on it. The catalog lists every artist, ones with no albums yet included. The cover in album view's title card and the photo in artist view are buttons: a click uploads a new picture (`hud/CoverUpload.tsx`, `store.setImage`, which also drops the stored colours so they're worked out again); an album's goes on every one of its songs too; Singles' cover stays drawn. The cover is a link or an uploaded picture, cropped and shrunk in the browser to a 320px JPEG and stored as a data: URL in `image` (`hud/thumbnail.ts`; `server/schema.ts` accepts base64 JPEG, PNG or WebP data: URLs up to 400 KB besides http(s) links). There's no way to remove things in the app for now (the trash icon is gone); `store.remove` is still there (hides a track, score kept; deletes a movie or book, or an album with its tracks and its artist if nothing else of theirs is left). Every track on an album is its own record, on the tree or not. Ids are always our own UUIDs; a Spotify id is only `vendor`, optional. Match catalogue picks by vendor id, never by name. Rank is the order of scores, and the gaps between them mean something.

Artists with an album on the tree (not hidden) hang at their raw artist score, capped at 100 (unrated: mid-spine); click one and every artist draws back into the spine, then that artist's albums come out at their album scores (`view.drill`, which also sets the zoom to albums). The zoom slider at the bottom of the rater's area (`hud/ZoomSwitch.tsx`, `view.zoom`: three stops, Artists · Albums · Songs; drag the knob, tap a stop or its word, or arrow keys; hidden in album view and split view; also in the list view, which lists that level) shows that level for every artist on the rater, or just `drill`'s, leaving out albums taken off in the catalog; at Songs the songs are draggable fruit as in album view, their covers shrinking as there are more of them, and labels dropping (cover alone) where there's no room. Esc, a click on empty space or the breadcrumb's Artists go back a step (`view.goBack`: album view, then the one artist, then the zoom back to artists). Artist view (`artistView` in `scene/view.ts`: `drill` set, outside album view and split view): the artist's overview fills the left half as album view's details do, and the rater moves right with their albums all on its right (`hud/ArtistView.tsx`: photo, name, albums and rated songs, grade beside score; Songs by tier, a bar per song tier, hover one for its songs best first, at most 8 then "and N more"; Career, their albums' scores in release order on `hud/AlbumChart.tsx`, dots in each album's grade colour; Albums, each with year, score and grade, a click opens album view, or puts a staged one on the tree; phones: the opener alone). Clicking an album on the rater (artist view or the Albums zoom) opens album view on it; Esc comes back to where it was. `view.logAction` and `hud/ActionLog.tsx` are still in the code but nothing logs or shows them now. Esc or a click on empty space goes back to the artists. Nothing on it is dragged or stored; marks are placed fresh each time (`placePieces`).
- **Scoring:** stored 0 (bottom of the spine) to 100 (top), always: the database, views, saving and heights don't change with the scale. Scores are *shown and entered* on the scale in use (`src/shared/scale.ts`, `SCALE`): now `FIVE`, 0–5 in steps of 0.1, which also snaps every rating (drag or typed) to its steps (2 stored points); `HUNDRED` (0–100, continuous, v1's tiers) is kept beside it. The scale holds the song tiers in shown units (FIVE: CLASSIC 4.7+, GREAT 4.5+, GOOD 4+, PLEASANT 3.75+, INTERESTING 3.5+, OK 3+, AVERAGE 2.5+, BAD 0.5+, OFFENSIVE below; `TRACK_TIERS` is them in 0–100); a tier goes by the score as shown (`roundToShown`), so the number and the tier always agree. Album scores show on the scale to two decimals (`formatPrecise`) and their letter grades go by that shown score (bounds stay 0–100: A+ = 4+); artist scores and artist grades aren't on any scale, so the Artists level's spine reads 0–100. Dragging a mark up or down sets its `score` (`positionToScore`); held on one score for a moment mid-drag, a card beside it fades in with the songs already rated there, or nearest within 2 points (`board.sameScore`, `hud/ScoreMatches.tsx`); unrated marks sit in rows round the middle, grey on dashed leaders and tagged Unrated, and count for nothing until dragged. Dropping a staged album on the spine puts its tracks on unrated and opens album view on it (that's where they get rated; `enterAlbumView` in `hud/Catalog.tsx`). A typed entry starts active rating: everything else on the page fades (marks, staged albums; the batch's album and artist stay bright) until each of the batch has a score, Esc, or the tree closes (`board.ratingFocus`, `view.rating`, `hud/RatingWatch.tsx`); it's view state, never saved. Album and artist scores are never stored or dragged: they're worked out from their tracks (`src/state/scores.ts`) with the v1 formulas. Album = average of its tracks (shown to up to two decimals: 71.43, 75.5, 89; `formatAlbumScore`, its letter grade by the rounded score), but only once every track on the rater (hidden ones aside) is rated: until then it's Incomplete (`isIncomplete`, `shownAlbumScore` in `scores.ts`; `rating()` gives the label `INCOMPLETE`), with no score or grade anywhere, mid-spine on the rater, left out of the Career chart and sorted with the unrated albums (the database view `music_album_scores` still averages the rated ones); artist = points for each rated track, by its song tier as shown (each tier's `points` in `scale.ts`; FIVE: CLASSIC 6, GREAT 4, GOOD 1, PLEASANT 0.5, INTERESTING 0.1, OK and below nothing; `artistWeight`), open-ended, shown to one decimal; hidden tracks still count. **Not a song** (`notASong` on a track, column `not_a_song`, migration 006: skits, spoken intros, interludes, hidden tracks…): stays in its album's tracklist, dim and tagged NOT A SONG, but is never on the rater (`treeNodes`) and counts for nothing: no score or tier, not in the album's average or completeness, the artist score, the score-match card, the list view or the song counts (the views and `/api/counts` skip it too); a score it had is kept, for if it's unmarked. Toggled per track in album view's EDIT (SONG / NOT A SONG); EDIT's ARTIST field also changes the album's artist (type to search, artists not loaded yet included, and pick one, or type a new name: NEW; SAVE loads their albums, then `store.moveAlbum` moves the album and its songs; Singles moved to an artist with Singles joins theirs; the artist it leaves goes if nothing of theirs is left); tracks whose name has the word "skit" are marked when added (`isSkit` in `src/shared/names.ts`). **Live** (`live` on a track, column `live`, migration 007): a live recording of a song the artist already has; rated and counted for its album as usual, but left out of the artist score and their Songs by tier (live albums stay on the Career chart); tagged LIVE after its name in the tracklist. Covers and songs that only exist live aren't marked, so they count. Marked when tracks are added (`state/live.ts`, `markLive`): a track that looks live (a live tag at the end of its name, or an album named as a live one: Unplugged, Live at/in/from/on…; `looksLive`) whose name without the tag (`songKey`) matches a studio track of the same artist on another album; a studio album added after the live one marks the live tracks it matches. Only ever marks: unmarking is EDIT's (a LIVE toggle per track, and ALL LIVE / NONE LIVE). The database views `music_album_scores` and `music_artist_scores` use the same formulas (the artist view, migration 005, hardcodes FIVE's tiers and rounding: change it with them). Anything beyond this (tiers, letter grades, bands) is undecided, so raise it with the user before building it.
- **Persistence:** Postgres. The schema is numbered SQL in `server/db/NNN.description.sql`, applied automatically at server startup and recorded in `schema_migrations`. Add new ones as the next number; never edit an applied one. Tables: `music_artists`, `music_albums` (`staged_at`, `added_at`, `misc`), `music_tracks` (links to album/artist, `score`, `tree_*` branch, `hidden`, `not_a_song`, `live`, `short_title`: one or two words the rater shows instead of the full name, set by `shortTitle` in `src/shared/names.ts` when a track is created and editable beside each name in album view's tracklist EDIT (blank: none, the rater shows the full name; it follows a rename while it's still the automatic one). The tracks from before it were filled in by hand on 2026-11-07), `movies`, `books`, plus the two score views. Album → artist and track → album/artist links are checked at commit; deleting an album deletes its tracks. **`npm run dev` runs the API under `tsx watch`, so editing any server file restarts it and applies new migrations to the real database immediately.** Stop the API before writing a migration, and dry-run it on a copy of the data first: a throwaway schema (`server/repo.test.ts` shows how), the migrations up to the previous one, a copy of the real rows, then the new one. The schema was squashed into `001.schema.sql` on 2026-11-06; older migrations are in git history only.
- **Saving:** the zustand store holds the state in memory and has all the logic. `src/state/remote.ts` loads `GET /api/state` at startup: the first page of artists (`ARTIST_PAGE`, 30, best first by artist score from the `music_artist_scores` view, unrated ones after by name), every movie and book, only the albums and tracks that belong to no artist, and a summary of each artist sent (`artistInfo`: score, album count, when their first album went on the tree, how many of their tracks are on it). More artists come a page at a time: reaching the bottom of the catalog loads the next 30 (`loadMoreArtists`, `useArtistPages`, `GET /api/library/artists/page?after=`, keyset-paged by an opaque cursor, so none is skipped if scores change; one sent again is ignored). Until their page has loaded, an artist isn't on the rater's Artists level, the list view or the compare picker. Anything that matches a catalogue artist looks unloaded ones up first so they're never added twice: `loadArtistsFor` (the ADD palette, the artist checklist, album details) asks `findArtists` (`GET /api/library/artists/find`, by Spotify id, exact name, or `q`, part of a name) for refs not matched locally, and ADD … as an artist checks the exact name before making a new artist. Artists from pages and lookups go into the store and the last saved state together. An artist's albums and tracks load when something needs them (`loadArtists`, `GET /api/library/artists?ids=`, once per artist per session): opening them in the catalog or their box, picking them on the rater or their overview, the Albums or Songs zoom for everyone, split view or the list view (`hud/LibraryLoader.tsx`), and the ADD palette for any artist it suggests or adds to (so an album is never added twice). They go into the store and the last saved state together, so loading never saves anything. Until an artist is loaded, read their score, albums and place on the rater through `state/board.ts` (`artistScoreOf`, `hasAlbums`, `firstOnTree`, `fruitCount`, `isLoaded`), never straight from `albums` and `tracks`; once loaded, they're worked out locally as before. The counts in the bottom-left corner (MUSIC: artists, albums, songs, a line each; other types: items) are the database's totals, not what's on the rater: `useCounts` in `state/remote.ts` asks `GET /api/counts` at startup and after each save. Anything that needs every song (the drag card's matches) asks the server (`GET /api/library/tracks/near`) and adds what's loaded locally. After each change it diffs each collection against the last saved state (`src/shared/sync.ts`) and sends upserts and deletes to `POST /api/sync`, debounced and retried. The server validates every batch (`server/schema.ts`) and applies it in one transaction (`server/repo.ts`). Only the open type is kept in the browser (localStorage `visual-rater-v2.ui`). Entity types shared by the app and the server live in `src/shared/model.ts`; components read the collections with `usePersisted()` (a shallow-compared selector), because a zustand selector that builds a new object every time re-renders forever.
- **Cover colours:** `colors[0]` on an album, artist, track, movie or book stores the raw dominant colour of its image, worked out once in the browser (`src/scene/color.ts`, `useGlow`) and saved. The 3D version drew glows from it (`glowColor()`); the 2D board doesn't show it yet, but keeps working it out so it's there. Never store adjusted colours.
- **Layout rules:** a rater is a vertical spine, 100 at the top, 0 at the bottom, numbered every tenth of the way on its left as the scale reads (0, 0.5 … 5; 0–100 at the Artists level), with a hairline across at each 10. Each mark hangs on a horizontal leader out to the left or right, a round cover ringed in its tier's colour, its label beyond it (a track's short title if it has one). Placement is worked out fresh from scores every time (`state/place.ts`, `placePieces`), never stored: rated marks at their height, each as close to the spine as clears the marks and labels already placed on that side (sides alternate, or are fixed: album view and split view put everything on the right); unrated marks fill rows round the middle, in their order (tracklist order in album view) read top to bottom, each row out to the available width, labels included, before the next starts (never back to an earlier row); the block of rows is centred on the middle, and on a rater too short for them all, marks drop their labels (cover alone) in the row they've reached rather than move on. The furthest out are drawn first, so leaders pass behind nearer covers. Marks can only be dragged up and down. Split view (MUSIC; `view.split`; its key, `hud/SplitKey.tsx`, is off the page for now while it's re-purposed, so nothing turns split view on, but the code all still works): every album on the tree gets a rater of its own, side by side in a row in the order they went on (`state/split.ts` for the order), in pairs back to back: the first of each pair hangs its marks left of a spine at the right of its column, the second right of a spine at the left of its, so each pair's spines sit close together (sides follow the place in the row, so they swap when a rater is dragged along it); the scale's numbers are once, at the start of the row; with the scale's hairlines running across the whole row, so one height is one score across it; the row scrolls sideways (a wheel scrolls it too), each rater has its album's caption under it, and dragging a caption moves that rater along the row (`view.raterOrder`, in memory only). Album view and the list view bring them back onto one rater while they're up (`isSplit`). The list view (`hud/ListView.tsx`, the TREE ⟷ LIST switch above the spine) is a table in place of the rater of whatever the zoom slider is on (MUSIC; the slider stays in the list view): artists or albums (just `drill`'s, as on the rater; score and grade, read-only, no pencil), or the songs; albums and artists taken off the rater with the catalog's boxes are left out at every level; moving the slider to Albums or Songs from the tree opens the list view, and back to Artists, or opening an artist's overview (catalog, breadcrumb), returns to the tree (`setZoom`, `setDrill` in `scene/view.ts`); and an album's title in it (the Albums list's names, the Songs list's ALBUM column) opens album view on it. Album view is always on the tree: opening it from the list view goes back to the tree (`setAlbumView`), and the TREE ⟷ LIST switch is hidden while it's open, in the rater's area (`scene/box.ts`, `useBox`, `areaLeft`); the catalog, breadcrumb (its first step reads the zoom's level there: Artists, Albums or Songs), album view and artist view stay. Every artist's albums load for the list of songs only (`LibraryLoader`). Each score in it can be typed in: the pencil left of it (on the row's hover; always on touch) turns it into a field, Enter or leaving it keeps a changed score (`store.move`); emptied, the song is unrated again, still on the rater (`store.unrate`); Esc lets it go; the rows slide to their new order (motion `layout`), and the list follows the changed row if it leaves the screen. Esc in any text field is the field's own: the capture-phase Esc handlers (`Catalog`, `RatingWatch`) skip inputs.
- **API (`server/`):** `GET /api/suggestions/:typeId?q=` (only `music`: Spotify artists, albums and songs, merged by name match), `GET /api/music/albums/:id` (album with full tracklist), `GET /api/music/artists/:id/albums` (an artist's albums, one per album across editions: `distinctAlbums`), `GET /api/state`, `GET /api/library/artists?ids=` (those artists' albums and tracks), `GET /api/library/artists/page?after=` (the next page of artists), `GET /api/library/artists/find?vendor=&name=&q=` (artists by Spotify id or exact name, both repeatable, or part of a name), `GET /api/library/tracks/near?score=&range=&limit=&exclude=` (rated songs at or near a score, with album and artist names), `GET /api/counts` (how many artists, albums (Misc aside) and songs are saved) and `POST /api/sync` (saving). Every `/api/*` response is gzipped when the browser accepts it (`hono/compress`). Validate ids and bodies before calling Spotify or the database. Album and track names from Spotify are saved without edition tags (`src/shared/names.ts`: a trailing (…), […] or " - …" naming a remaster, deluxe, expanded, anniversary or similar edition; live, remix, acoustic, radio edit and feat. stay); a suggestion keeps the removed tag as `edition`, shown dim in the ADD palette only.
- **UI tenet:** minimalist. No forms or panels; everything is a gesture on the page or goes through the ADD palette. Don't add hint text the user didn't ask for. Keep touch targets around 44px, and inputs at 16px or more so iOS doesn't zoom.
- **Checks:** `npm run typecheck`, `npm test` (vitest; covers store, layout, sync, server). The repository tests run against a real Postgres when `V2_TEST_DATABASE_URL` is set (e.g. to `visual_rater_v2`); they work inside a throwaway schema and drop it afterwards. To run an API against a throwaway schema, set `V2_DATABASE_SCHEMA`. Never point tests at the real tables: the one-time import only runs into an empty database. Check visual changes in a browser on desktop and a phone-sized viewport.
- `v2/.npmrc` sets `legacy-peer-deps=true`. npm 11 crashes ("reading edgesOut") resolving vitest's optional peer dependencies; every real peer is an explicit dependency, so this is safe.

## Data model (v1)

- Every v1 rater writes the same thing: a single numeric `score` per song, from 0 to 100. The tier thresholds are in `backend/db/04.song_score_update.sql` and `frontend/src/models/ScoreModels.ts`. Artist and album scores are calculated from song scores by database triggers.
- DB migrations are hand-numbered SQL in `backend/db/NN.description.sql` and applied manually. Add new ones as the next number; don't edit applied files. Hibernate `ddl-auto: update` also runs, so check that entity changes and migrations agree.
- `backend/backup.sql` is a data snapshot, not a migration.
- Full DB backup (schema, data, functions, triggers) taken 2026-11-03, before a possible rework: `~/projects/04-todo/code-visual-rater/db-backups/visual_rater-20261103-0731.dump` (restore with `pg_restore`), plus a plain-SQL copy `visual_rater-20261103-0731.sql` in the same folder. It doesn't include the `visual_rater_app` role; create that first. If the project folder moves to another status folder under `~/projects/`, the backups move with it.

## Conventions

- Commit messages are prefixed with the area: `(frontend) …`, `(backend) …`, `(imageservice) …`, `(both) …`, `(v2) …`.
- Branch from `main`. `origin` is `github.com:ed-khalid/visual-rater`. The `frontend`, `backend`, and `imageservice` remotes are leftovers from the merge; don't push to them.
